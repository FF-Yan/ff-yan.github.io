Software lifecycle & process

User story 的结构

模板：As a ⟨role⟩, I want ⟨capability⟩ so that I can ⟨benefit⟩. 三个部分各有要求：

部分要求常见的坏例子
Role（who）真实用户的角色，比如 Canvas 里的 instructor、TA、student“As a user”（太笼统）、“As a developer”、“As the server”
Capability（what）软件让这个角色能做的一件具体的事，用动词思考写成一个产品或技术：“I want a React app with a database”
Benefit（why）对用户的价值；不服务这个价值的功能可能不该做缺失，或者只是重复 capability：“so that it works”

好的 story 短到能写在一张卡片上，满足 INVEST+E：Independent、Negotiable、Valuable、Estimable、Small、Testable，再加 Ethical。User story 主要描述 functional requirements；performance、security、usability 这类 non-functional requirements 要另外列。

Conditions of satisfaction（CoS）

  • 每条 CoS 是一个从用户角度描述、可以测试的行为，在 story 内编号（1.1、1.2…），并且有优先级。
  • 优先级：E（Essential）没有它产品就没用；D（Desirable）没有它不好用但还能用；X（Extension）可能超出这次的范围，留给下个版本。
  • MVP = 选中的 stories 的所有 Essential CoS。一个 story 的 Essential CoS 都实现了，这个 story 就算完成。
  • 同一个 story 可以有好几套合理的 CoS，补细节本身就是设计。否定式的 CoS 也可以有，比如“非管理员不能修改优先级（E）”。

从 CoS 到测试（M2）

CoS →（分析、和客户协商）→ testable behaviors →（设计、协商）→ executable tests →（写代码）→ working code。一条 CoS 常常拆成好几个行为，比如“添加学生”要求返回一个 ID，并且这个 ID 和已有的都不同。写测试的过程会暴露没说清楚的地方（例如用不存在的 ID 查成绩单该怎么办），这些要回去和客户协商，不能自己猜。

Agile vs Waterfall

WaterfallAgile
Philosophy一开始把计划做完整，按 requirements → design → implementation → test 顺序推进，不回头一开始不可能知道所有事情，短周期迭代、小步持续发布。Agile Manifesto：individuals and interactions、working software、customer collaboration、responding to change 优先
Risk management阻止变化来降低风险：计划固定，每个阶段内控制风险；理由是越晚发现的缺陷修起来越贵（指数增长）拥抱变化来降低风险：time-boxing，每个 sprint 结束重新评估，走错方向能很快发现
谁负责 QA每个阶段结束有正式的 QA 关卡，文档很重，按阶段分工所有人（collective ownership）：TDD、code review、CI/CD，持续检查 functional 和 non-functional 质量
适合寿命长、风险高、需要大量 QA 的项目（国防、航天）需求不确定、要边做边学的产品

Agile practices

  • Team sizes：two-pizza team（两张披萨能喂饱的人数），沟通负担小。Brooks’s Law：给已经延期的项目加人只会更晚，因为沟通链路随人数增长。自组织的团队比层级式管理效果好；product team 端到端负责一个功能。
  • Sprint organization / Scrum：product backlog（stories 和 CoS，按优先级排序，持续更新）→ sprint planning（按优先级挑，拆成每个不超过一天的任务，用 T-shirt size 之类的相对大小估算）→ sprint backlog → daily scrum（不超过 15 分钟：做了什么、在做什么、卡在哪）→ increment → sprint review（看产品：demo 和交付的价值）→ retrospective（看流程：哪里可以改进）。Time-box 的意思是时间固定，范围调整。拿不准的工作先安排 “Sprint 0” 做调研和原型。
  • Knowledge sharing：降低 bus factor（不能只有一个人懂某块代码）。Pair programming（driver + navigator）大约少 15% 缺陷，但要多花 15–100% 的工作量。Code review 除了找 bug，也在传播知识。同一件事给两个人以上讲过，就写成文档。
  • YAGNI（You Aren’t Gonna Need It）：未来需要什么不确定，不要提前做推测性的功能。做错了要付开发和维护的成本；做对了但做早了，也会拖慢更重要的工作。YAGNI 不等于跳过设计或测试。
  • HRT pillars：Humility（不以自己为中心，承认会犯错）、Respect（真心在乎队友和他们的工作）、Trust（相信别人能干好，放手让他们做）。Code review 时把“你写错了”改成“这段控制流我没看懂，用 X 模式会不会更清楚？”
  • Blameless postmortem：惩罚个人会让大家隐瞒细节，根本原因永远修不好（blame spiral）。复盘时问：做了什么、看到了什么、原本预期什么、做了什么假设、时间线是怎样的；再列 went well / went wrong / got lucky，最后定 action items，每项有负责人和期限。Blameless 不等于没人负责，它针对的是系统里的原因。

常见错误

  • Role 写成 “user”，capability 写成产品或技术，benefit 只是重复 capability。
  • CoS 不可测（“easy to use”）、写成实现细节（“uses PostgreSQL”）、或者没有编号和优先级。
  • 以为 story 要所有 CoS 都做完才算完成：只需要 Essential 的。
  • 说 “Waterfall 总是不好”：slides 明确给了它适合的场景。
  • 以为 Agile 不做计划、不写文档：它只对近期工作做详细计划，文档写够用就好，对 QA 的要求反而更高。
  • 以为加人能赶进度（Brooks’s Law），或者把 stand-up 当成向经理汇报的长会。

Design patterns & principles

Web level：HTTP、REST、WebSocket

方式特点适合
HTTPrequest/response 成对出现，总是由 client 发起，所以是 pull像函数调用一样的交互（RPC）
REST基于 HTTP 的一种 RPC 风格，stateless：server 不记得某个 client 之前做过什么资源的增删改查；GameNite 的路由也常被叫作 REST API
WebSocketclient 打开后一直保持的双向连接，server 可以主动 push 事件；client 之间不直接通信，都经过 server 转发聊天、实时通知；只用 HTTP 的话只能轮询（polling），又慢又浪费

Controller-Service-Repository

层负责不知道
Controller和 client 通信：路由、用 Zod 校验请求、调用 service、返回响应。越薄越好数据怎么存
Service业务逻辑（比如 GPA 怎么算）client 怎么连接、数据怎么存
Repository唯一负责持久化的一层（Keyv、MongoDB、文件……）。很慢，所以方法返回 Promise业务规则

核心思想是 information hiding：可以换数据库而不动 service，service 可以单独测试。Async 会向上传染：调用了 async repository 的函数自己也必须是 async。

Scaling 与 microservices

  • Vertical scaling：换更大的机器，通常用在数据库上，迟早会碰到上限。
  • Horizontal scaling：多跑几份 controller/service。能这样做是因为 C-S-R 让 service 不保存状态，状态都在 repository 里。
  • Monolith（比如 GameNite）：一个程序、一个数据库，中小型系统更简单。
  • Microservices：很多小服务，各自独立部署、扩展，可以用不同的语言和硬件（Netflix 有几百个）。代价是跨服务的数据一致性、service discovery、整体复杂度；系统足够复杂之后才划算。

Code level：style guide、cognitive load、五条原则

开发者大约 70% 的时间在读、理解代码。短期记忆只能装大约 7±2 个 “chunk”；好的命名、一致的风格和短小的函数能让读者把代码组成更大的 chunk，降低 cognitive load。Style guide 的价值在于一致，用哪一套反而不重要；让 ESLint 和自动缩进来强制执行（缩进不对会让人误以为某行在 if 里面）。

课程的 Five Principles（不是 SOLID）：

原则意思违反的例子
1. Use names and indentation wisely名字要说明意思；返回值的函数用名词（c.diameter()），动作用动词（addItem）；相似的名字行为要一致变量叫 t、d、r；有的 get… 会 throw，有的不会
2. Make your data mean something选好要表示的信息和表示方式，并用名字、类型、注释写清楚怎么解读BoundingBox {x, y, width, height} 不说明 (x, y) 是中心还是角、单位是什么
3. One method, one job一个函数（类）只做一件事，也就是 Single Responsibility一个函数既算价格又写数据库又发邮件
4. Don’t Repeat Yourself多处用到的值起个名字；重复的步骤写成函数，差异变成参数（single point of control）几乎一样但有细微差别的复制粘贴代码（near-miss clones）
5. Identify and use good abstractions从问题描述里找出抽象，用类型表示，并写下不变量magic number 1.06；一长串硬编码的 if 税率表

Interaction level

  • Pull（demand-pull）：consumer 需要时去问 producer（clock.currentTime()）。简单，但大量频繁轮询会压垮 producer。
  • Push（observer / listener / pub-sub）：producer 保存 listener 列表，数据变化时通知所有人；consumer 用 addListener 注册。判断规则：数据变得慢、被要得勤 → push；数据变得比需要的快 → pull。
  • Callback / delegate：把一个函数交给 producer，让它以后调用。React 的 onClick 就是：浏览器是 producer，你的代码是 consumer。
  • Dependency injection：构造函数接收一个接口（比如任何 IPullingClock），而不是自己 new 具体实现，方便替换和测试。
  • Singleton：全系统只有一个实例。课程的写法：class 不 export；模块里有个初始为 null 的变量；export 一个 instance() 函数，第一次调用时创建，之后都返回同一个。代价是相当于全局状态，测试之间不够独立。
  • First-time-through switch：“还没创建就创建”的那个判断，用于延迟、只做一次的初始化（项目里每个 repository 第一次访问时才建 Keyv store）。

Layered / Tiered每层一个职责，只调用下层（向上用 callback）；分在不同机器上就叫 tierOS kernel、三层 web app、C-S-R；需要定义清楚的接口

常见错误

  • Five Principles 写成 SOLID。可以补一句 one method/one job 就是 SRP。
  • 把 REST 和 HTTP 当成一回事；以为 WebSocket 让 client 之间直接通信。
  • 业务逻辑写进 controller，或者 service 直接访问存储。
  • 把 “stateless service” 理解成整个 app 没有状态：状态在 repository 里。
  • Vertical / horizontal 搞反；说 microservices 总是更好而不提代价；说 push 总比 pull 好。
  • Observer 的角色搞反：保存 listener 列表的是 producer（subject）。
  • 把 singleton 说成“就是全局变量”，没提隐藏 class 和 accessor + first-time-through switch。
  • Pipeline（线性、固定顺序）和 event-driven（队列、多个 outbox、可分叉）混淆。

Async

目标：用 concurrency 掩盖 latency

CPU 大约 1 ns 执行一条指令，而网络、磁盘 IO 慢好几个数量级。与其干等，不如在等的时候做别的事，这就是 masking latency with concurrency。JS 靠两样东西做到：non-blocking IO（fetch、setTimeout、文件读写交给 Web APIs，返回 promise）和 cooperative multitasking（同一时间只跑一个任务，任务自己让出）。

async/await

  • async 函数总是返回 Promise（pending → fulfilled 或 rejected）。
  • await 只暂停当前这个函数，把控制权还给调用者和 event loop，不会卡住整个程序。只能在 async 函数里用。
  • 第一个 await 之前的代码是立刻同步执行的。
  • 被 reject 的 promise 会让 await throw，用 try/catch 处理。
  • 忘了 await（floating promise）拿到的是 Promise 对象本身，会打印出 [object Promise]；lint 会报。

Run-to-completion 与 critical section

JS 只有一个 call stack，一个任务开始了就跑到 stack 清空为止，不会被中途打断。函数只会在 await（或 return）处暂停，两个 await 之间的代码就是一个 critical section，别的代码插不进来。对比 Java 这类 preemptive threads：线程可以在任何地方被打断，还共享内存，到处都可能有 data race，需要锁。

但 async 不会消除 race：一个“读 → 检查 → 写”的操作如果中间跨了 await，别的任务可以在那里插进来（Bank activity：两笔 $75 取款同时读到余额 $100，都通过检查，一共取走 $150）。修法是用 lock 把整个“读 → 检查 → 写”包成一个 critical section，并且在 finally 里释放锁。

Event loop：call stack、Web APIs、task queue

  1. 同步代码在 call stack 上执行。
  2. 遇到 async 工作（timer、fetch）就交给 Web APIs，JS 继续往下执行。
  3. Web API 的工作完成后，回调或 await 之后的代码进入队列。
  4. 只有 call stack 空了，event loop 才从队列取下一个：先把 microtask queue（promise 的后续、await 之后的代码）清空，再取一个 macrotask（setTimeout、IO 回调）。

Promise.all：把 Promise<T>[] 变成 Promise<T[]>。几个互不依赖的请求一起发出去，总时间约等于最慢的那个（3 个 1 秒的请求依次 await 要约 3 秒，用 Promise.all 约 1 秒）。结果按传入的顺序返回，不是按完成顺序；任何一个 reject，整体就 reject。

例题：打印顺序

const wait = (ms: number) => new Promise<void>(r => setTimeout(r, ms));
async function load(name: string) {
  console.log(`load start ${name}`);
  await wait(100);
  console.log(`load done ${name}`);
}
console.log('main start');
setTimeout(() => console.log('timer 0ms'), 0);
load('x');
Promise.resolve().then(() => console.log('microtask'));
console.log('main end');

按顺序写出打印结果，并用 call stack / Web APIs / queue 解释。

Answer

main start → load start x → main end → microtask → timer 0ms → load done x

The whole script runs to completion first: load runs synchronously up to its await, which hands a 100 ms timer to the Web APIs and suspends load. Once the stack is empty, the event loop drains the microtask queue (microtask), then takes one macrotask (the 0 ms timer). About 100 ms later the timer resolves and the rest of load runs as a microtask. A 0 ms timer is not “immediate”, and nothing interrupts synchronous code.

常见错误

  • 说 await 会卡住整个程序：它只暂停当前函数。
  • 以为 async 函数里的代码全都“晚点执行”：第一个 await 之前的部分立刻执行。
  • 以为 setTimeout(f, 0) 马上执行：它要等同步代码和所有 microtask 跑完。
  • 以为 async/await 能防止 race：它只保证两个 await 之间不被打断。
  • 以为 Promise.all 按完成顺序返回结果。
  • 把 concurrency 理解成多线程并行：JS 只有一个线程，是 IO 和计算重叠。

Testing

TDD 与 Vitest

TDD：从 CoS 写出测试，先让测试失败（red），再写刚好能通过的代码（green），然后 refactor，再加强测试，循环。测试定义了什么叫“做完”，写测试会逼你把问题想清楚，还会暴露需求里的歧义。局限：测试不可能规定所有输入和行为，大量按功能写的测试维护成本也高。

Vitest要点
describe / it / expecttest suite / 单个测试 / 断言
toBe vs toEqual vs toStrictEqual同一个对象或原始值相等 / 深比较内容 / 深比较且不放过 undefined 属性
expect(() => f()).toThrowError()必须把调用包在函数里，否则 throw 发生在 expect 之前
beforeEach / afterEach每个测试用新的 fixture（比如新数据库），测试之间互不影响
AAAAssemble（准备）、Act（执行）、Assess（断言）

Test adequacy：测试够不够

  • 三个标准：输入够不够、执行到的代码够不够（coverage）、测试能不能抓到可能的 bug（mutation testing）。
  • Contract 比 type 更能指导选输入：number 不排除 3.1、-8、NaN。Unit test 只需要满足前置条件的输入；但来自外部的输入（HTTP body）要当成 unknown，用 Zod 校验，并测试非法情况。
  • 选输入：范围两端加中间，一定要试 0；同一个 equivalence class 选一个代表；搜索要试找到和找不到。
  • Coverage：statement / line 最粗；branch（每个判断的两个结果都要走到）是业界常用标准；function 看每个函数是否被调用；path coverage（所有分支组合）实际做不到。
  • 100% coverage 不代表没有 bug：执行到不等于检查过。没有断言的测试也能贡献 coverage；某个特定分支组合才触发的 bug 也会漏掉。Coverage 的真正用处是找出你以为测了其实没测的代码。
  • Mutation testing（Stryker）：自动生成有小改动的 mutant（比如 >= 改成 >）。测试没发现就是 survived，说明断言太弱，要补一个原版通过、mutant 失败的测试。有些 mutant 行为等价或只改了 contract 之外的行为（innocuous），为了杀它去断言精确的错误信息是 overspecification。

Test doubles：fake、mock、spy

类型是什么Vitest
Fake手写的替身不需要库，但费工、接口一改就要跟着改
Mock自动生成、会记录调用的替身vi.fn()（默认返回 undefined）、mockReturnValue、mockResolvedValue、mockImplementation；断言 toHaveBeenCalledTimes、toHaveBeenCalledWith
Spy包住真实对象的方法，记录调用；除非覆盖，否则真实实现照常执行vi.spyOn(obj, 'method')，用 mockRestore 还原

用 test double 是为了替换不受控制的东西（网络、数据库、用户），并检查副作用（发了什么、存了什么）。mockClear 只清调用记录，mockReset 还会清掉实现，测试之间要重置，否则会出现测试顺序依赖。缺点：mock 编码的是你的假设，抓不到集成 bug；spy 让测试依赖实现细节，容易变脆。

测试的层级

层级问的问题特点
Unit这个单元符合它的规格吗？快、稳定、容易定位错误；用 test double 隔离依赖
Integration几个模块合起来能正常工作吗？抓模块之间错误的假设，这是 mock 抓不到的
E2E真实的用户流程在真实浏览器里走得通吗？最真实，但慢、容易 flaky、难定位；只覆盖最重要的流程
Acceptance客户满意吗？黑盒、从用户角度，常写成 given/when/then

Google 的 test pyramid：约 80% unit、15% integration、5% E2E。反过来大部分靠手动和 GUI 测试叫 “ice-cream cone” anti-pattern。CD 不是一个测试层级，而是交付流程，在发布之后继续做 QA。

Flaky test（时过时不过）最常见的原因是 async wait（等某件事在超时内完成），其次是测试顺序依赖和并发。不要依赖时间和顺序，给足资源，分清是 flaky 还是真 bug。

Playwright：在真实浏览器里跑 UI/E2E 测试，同样是 AAA。按用户的方式找元素（getByRole、getByLabel、getByText），不用 CSS 选择器；操作会自动等待元素可用；用会重试的断言 await expect(locator).toBeVisible() 和 waitForURL，不要写固定的 sleep。

Testing async code

  • 测试函数本身写成 async，并且 await 被测的调用或断言：await expect(p).resolves.toEqual(v)、await expect(p).rejects.toThrowError()。
  • 不 await 的话，测试可能在 promise 落定之前就结束，于是“假通过”。expect.assertions(n) 能确认断言真的执行了。
  • expect(() => asyncFn()).toThrow() 是错的：async 函数是 reject 它的 promise，不会同步 throw。
  • 用 mockResolvedValue 代替真实的异步依赖。

Code review 与 CI/CD

  • Code review：找出测试抓不到的设计、可读性和逻辑问题，同时传播知识、维持团队规范。它和自动化测试互补，不能互相替代：lint 和测试交给 CI，reviewer 专注于设计。
  • CI：每次提交或 PR 都自动构建、跑测试，给每个开发者全局反馈。流程：develop（code review）→ build（style check、编译、unit tests）→ test（integration、load tests）→ deploy（E2E）→ monitor（KPI）。好的 CI 要快、确定性强，不能让 build 一直坏着；每次只放一个改动，出错时才能定位是谁。
  • CD：小批量、频繁、分阶段发布（dev → test → staging/dogfood → production），配合监控和回滚。手段：canary（先给 5% 用户）、A/B test、feature flag、自动回滚。CD 不等于“马上上线”。
  • 重 TDD 的团队维护大量测试；以 CD 为中心的团队测试少一些，靠监控和 canary 在发布后把关。Knight Capital 手动部署漏了一台服务器，45 分钟亏损约 4.4 亿美元：部署要自动化，并且要监控。

常见错误

  • “100% coverage 就说明测试足够”；line coverage 和 branch coverage 混为一谈。
  • 以为每个 survived mutant 都是 bug。
  • 以为 vi.spyOn 会自动替换实现（不会，真实方法照常执行）；测试之间不重置 mock。
  • async 测试没写 async/await；用固定 sleep 等待 UI。
  • 觉得 E2E 测试越多越好；把 snapshot test 当成“正确性”测试（它只检查“和上次一样”）。
  • CI 和 CD 混淆；把 TDD 理解成“先写完所有测试再写所有代码”。

React

Component、props、state

Component 把一个界面部件的 state、逻辑和呈现放在一起，是一个返回 JSX 的函数；整个 app 是一棵 component 树。State 变了，React 就重新 render，让页面和 state 保持一致。

PropsState
从哪来父组件传进来组件自己用 useState 创建
能不能改只读，子组件不能改只能通过 setter 改
变化时父组件用新 props 重新创建子组件时 re-renderstate 变化时 re-render；父组件 re-render 时子组件保留自己的 state
  • Setter 是请求，不是赋值：React 收集这些请求，统一应用后再 re-render，所以新值要到下一次 render 才看得到。同一个 handler 里调用三次 setCount(count + 1)，三次读到的都是同一个旧值，结果只加 1；用 setCount(c => c + 1) 才加 3。
  • 父子通信：往下传 props；往上是父组件把 handler 当作 prop 传下去，子组件调用它。几个子组件共享的 state 放在共同的父组件里。
  • State 要当作不可变：改了对象再用同一个 reference 调 setter，React 认为没变，不会 re-render。新增用 [...arr, x]，删除用 filter，替换用 map，排序前先复制；对象用 {...obj, y: 10}。
  • Controlled input：value={title} 加 onChange={e => setTitle(e.target.value)}。

Reconciliation 与 key

直接操作 DOM 很慢，所以 React 把新的 render 结果和上一次比较，只更新变了的部分，这叫 reconciliation。列表靠 key 认出哪个元素对应哪个子组件，所以 key 必须是稳定、唯一的 id。用数组 index 当 key 时，删掉第一项后剩下的元素 key 都变了，React 会以为删的是最后一个，把第一个组件实例（连同它的旧 state）留给了别的数据。

useEffect

用来让组件和外部系统保持同步：定时器、订阅（socket）、fetch、外部库。

依赖数组effect 什么时候运行
[]只在第一次 render 之后（开发模式的 StrictMode 会故意多跑一遍 mount）
不写每次 render 之后
[a, b]a 或 b 变了之后。比较的是 reference，对象内部的字段变了但还是同一个对象，就不算变化

Cleanup（effect 返回的函数）在两个时候运行：同一个 effect 下一次运行之前，以及组件 unmount 时。[] 的 effect 只有 unmount 时才会 cleanup。用它取消订阅、清定时器、关闭 socket，否则 listener 会越积越多（内存泄漏），还会更新已经卸载的组件。

Custom hooks 与 rules of hooks

Custom hook 是用 useState、useEffect 组合出来的 useX 函数，作用是把业务逻辑和显示逻辑分开：组件只负责显示，逻辑可以复用、单独测试。Hook 的 state 属于调用它的组件，hook 里的 setter 会让那个组件 re-render。例子：useClock(listener) 隐藏订阅和取消订阅；useToDoItemList() 返回 {todoList, handleAdd, handleDelete}。

Rules of hooks：只在组件或 custom hook 的顶层调用 hook，不能放在 if、循环或嵌套函数里，因为 React 靠调用顺序区分不同的 hook。Lint 规则 react-hooks/exhaustive-deps 会检查 effect 里用到的变量是否都写进了依赖数组。

例题：停在 1 的秒表

function Stopwatch() {
  const [seconds, setSeconds] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setSeconds(seconds + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []);
  return <p>{seconds} s</p>;
}

页面显示 1 之后就不动了。为什么？怎么修？

Answer

With [] the effect runs only once, so the interval callback closes over the first render’s seconds, which is 0: every tick requests setSeconds(0 + 1). Fix it with the updater form, setSeconds(s => s + 1), which always gets the current state, so the effect can keep []. Adding seconds to the dependency array also works but tears down and recreates the interval every second; either way the cleanup clears the interval on unmount.

常见错误

  • 调用 setter 之后马上读 state，以为已经是新值；在 timer、listener 的闭包里用 setX(x + 1)。
  • 直接改 state（push、sort、obj.f = …）再用同一个 reference 调 setter。
  • 以为依赖数组能发现对象内部的变化；把 [] 和不写搞混。
  • 以为 cleanup 只在 unmount 时运行。
  • 子组件试图修改 props；用 index 当 key；在条件或循环里调用 hook。

按考试题型写的题，参考答案是英文的 1–4 句。先在作答框里写，再点 Copy question，把题目、你的答案和参考答案一起粘贴给 Claude，请它批改并指出漏掉的点。

Q1 · Process：修改 user story

What is wrong with this user story, and how would you rewrite it? “As a user, I want a React app with a leaderboard database so that it works.”

Answer

“User” is a cop-out role, the capability names a product and technology rather than something a person does, and “so that it works” gives no user benefit. A better story: “As a competitive chess player, I want to compare my rating with my friends’ ratings so that I stay motivated to keep playing,” followed by numbered, prioritized CoS such as “1.1 I can see my friends ranked by rating (E).”

Q2 · Process：Waterfall vs Agile

Compare how Waterfall and Agile manage risk, and who is responsible for quality in each.

Answer

Waterfall reduces risk by preventing change: the plan is fixed up front and each phase ends with a formal, document-heavy QA gate, because defects cost exponentially more to fix in later phases. Agile reduces risk by embracing change: work is time-boxed into short sprints with small, continuous releases, so a wrong direction is caught early. In Agile, quality is everyone’s job (collective ownership) through TDD, code review and CI/CD.

Q3 · Process：scenario

PayFast’s 12 developers all report to one manager, and only Dana understands the billing module. Two weeks before launch the team is behind, so the VP adds six contractors. On Friday, Dana’s rushed change takes billing down; at the all-hands the manager names Dana as the cause and requires sign-off on all her commits. Identify three problems and the course practices that address them.

Answer

Billing has a bus factor of one; pair programming and code review would spread that knowledge. Adding contractors to a late project violates Brooks’s Law, since every new person adds communication links; small self-organizing teams and renegotiating scope would work better. Publicly blaming Dana will make engineers hide details, while a blameless postmortem (actions, observations, assumptions, timeline, action items with owners) would find the real cause, such as deploying without CI or review.

Q4 · Process：YAGNI

A developer wants to spend this sprint building a generic plug-in system for future payment providers, although only Stripe is required. What do you advise?

Answer

YAGNI: we don’t know which providers we will really need, and a speculative feature costs time to build, costs upkeep while unused, and delays higher-priority backlog items. Build the simplest design that meets the current CoS, protect it with tests, and refactor toward a plug-in system only when a second provider actually reaches the backlog.

Q5 · Design：scenario

TutorMatch is a 4-person startup. Each Express route handler validates input, runs the matching algorithm and writes SQL directly. Students only see new messages after refreshing the page. During finals the single server is overloaded, and the CTO wants to split the app into 12 microservices right away. What do you recommend?

Answer

First refactor to Controller-Service-Repository: controllers validate and translate HTTP, the service holds the matching logic, and only the repository touches the database, which hides information and makes the logic testable. Use WebSockets so the server pushes new messages instead of clients polling. Because the service then keeps no state of its own, it can be scaled horizontally by running more copies, with the database scaled vertically. Twelve microservices would add consistency, service discovery and operational complexity that a 4-person team doesn’t need yet.

Q6 · Design：code review

function handle(d: any) {
  let r = 0;
  for (const i of d.items) r += i.p * i.q;
  r = r * 1.0625;
  db.save(d.id, r);
  emailUser(d.user, "Total: " + r);
  return r;
}

Which of the course’s design principles does this function violate, and how would you improve it?

Answer

The names handle, d, r, p, q tell the reader nothing (names), and any with undocumented fields gives the data no stated meaning; define Order/LineItem types (meaningful data). It does four jobs — subtotal, tax, saving and emailing — so split it into separate functions, with saving in the repository (one method, one job). Q7 · Design：push vs pull

A campus shuttle tracker gets a new GPS fix every 30 seconds, and 2,000 phones want the location every second. Should the app push or pull? When would the other choice be right?

Answer

Push: the data changes far more slowly than it is requested, so the tracker should keep a list of listeners and notify them on each update (Observer over WebSockets) instead of answering 2,000 polls per second. Pull is better when the data changes faster than anyone needs it, such as a sensor sampling 1,000 times a second behind a dashboard that is opened occasionally.

Q8 · Design：architecture

Name the architecture pattern for each: (a) VS Code extensions; (b) cat log | grep ERR | sort; (c) an “order created” event that triggers payment, inventory and email units in parallel; (d) a weekend hackathon script.

Answer

(a) Plug-in / microkernel: a small core with extension points. (b) Pipeline: stages in a fixed processing order. (c) Event-driven: units consume events from queues and emit their own, so the flow can branch. (d) Anarchic: fine for one developer on a short-lived project, painful once others join or the code must be maintained.

Q9 · Design：singleton

How does the course implement a singleton in TypeScript, and what is one benefit and one cost?

Answer

The class is not exported; an exported instance() function checks a module-level variable and creates the object the first time it is called (the first-time-through switch), then returns that same object every time. This guarantees one shared instance, such as one Keyv store per repository, created only when first needed. The cost is that it is effectively global state, so tests are less independent.

Q10 · Async：太慢的 dashboard

A dashboard runs const u = await getUser(); const p = await getPosts(); const f = await getFriends();. Each call takes about one second and none depends on another. Why is it slow, and how would you fix it?

Answer

Each await suspends the function until that response arrives, so the independent requests run one after another and take about 3 seconds. Start all three at once with await Promise.all([getUser(), getPosts(), getFriends()]): the requests overlap in the Web APIs, the total is about the slowest one (1 second), and the results come back in the listed order. This masks latency with concurrency.

Q11 · Async：可能的输出

printA awaits a random delay and then logs “A”. printBC awaits a random delay and then logs “B” and “C” with no await between them. Both run through Promise.all. Which outputs are possible, and would Java threads differ?

Answer

Only ABC or BCA. B and C are in the same critical section, and JavaScript runs each task to completion without preemption, so nothing can print between them. With preemptive threads, as in Java, a thread could be interrupted between B and C, so BAC would also be possible.

Q12 · Async：data race

withdraw awaits a read of the balance, checks that it is large enough, then awaits a write of the new balance. Two $75 withdrawals against a $100 balance run through Promise.all, and both succeed. Explain and fix.

Answer

Each withdrawal yields at its first await, so both read $100 before either writes, both pass the check, and $150 is paid out. Run-to-completion only protects code between awaits, and this read-check-write spans one. Wrap the whole read-check-write in a lock (releasing it in finally) so withdrawals on the same account are serialized; the second one then sees $25 and fails.

Q13 · Async：floating promise

async function main() {
  const res = fakeRequest(32);
  console.log(`returned: ${res}`);
  console.log('done');
}

What does this print, and what is wrong?

Answer

It prints returned: [object Promise] and then done almost immediately; the request finishes later and its result is never used. fakeRequest returns a promise, and without await you log the promise object instead of its value. Fix: const res = await fakeRequest(32); — the no-floating-promises lint rule catches this.

Q14 · Testing：coverage vs mutants

Your test suite has 100% line and branch coverage, but Stryker reports 5 surviving mutants. Your manager says testing is done. How do you respond?

Answer

Coverage only shows that the code ran, not that the assertions would notice wrong behavior, so surviving mutants mean the tests are too weak. For each mutant that is a real bug, add a test the original passes and the mutant fails, such as a boundary case for a >=-to-> change. If a mutant is innocuous (equivalent, or only changes behavior outside the contract), document why instead of overspecifying the tests.

Q15 · Testing：太弱的测试

it('rejects bad auth', async () => {
  await socketJoin(mockSocket, mockServer)({ auth: badAuth, payload: id });
  expect(logSocketError).toHaveBeenCalled();
});

What is weak about this test, and how would you strengthen it?

Answer

It passes if anything logged any error, and if mocks aren’t reset between tests, a call left over from an earlier test can make it pass too. Assert the exact call with toHaveBeenCalledTimes(1) and toHaveBeenCalledWith(...), and reset mocks in afterEach. Also assert that mockSocket.join and emit were never called; otherwise a mutant that joins the room before checking auth would still pass.

Q16 · Testing：async 测试

it('rejects bad credentials', () => {
  expect(enforceAuth({ username: 'u1', password: 'no' })).rejects.toThrowError();
});

Why can this test pass even when enforceAuth is broken?

Answer

The test isn’t async and the expect isn’t awaited, so the test can finish before the promise settles and the assertion is never really checked. Make the test async and write await expect(...).rejects.toThrowError(), optionally with expect.assertions(1).

Q17 · Testing：flaky E2E

A Playwright login test fails about 1 in 10 CI runs but always passes locally. What is likely wrong, and how do you fix it?

Answer

It is flaky, most likely because it acts or asserts before a redirect, data load or the server is ready, or because it shares data with other tests. Use waitForURL and retrying assertions such as await expect(locator).toBeVisible() instead of fixed sleeps, create unique test data, and avoid depending on test order. Keep E2E tests few and push logic checks down to unit and integration tests.

Q18 · Testing：CD 没有 TDD

A startup with few automated tests wants to deploy many times a day. Is that viable, and what safeguards would you require?

Answer

Yes, continuous delivery can work without heavy TDD by moving more QA after release: small changes behind feature flags, staged rollouts or canaries, monitored KPIs with alerts, and automatic rollback. Keep a fast CI gate of unit tests and lint, and automate deployment to avoid Knight Capital–style manual mistakes. The trade-off is that some bugs reach real users and are harder to localize, which is unacceptable in safety-critical systems.

Q19 · React：setter

A click handler calls setCount(count + 1) three times. Starting from 0, what does one click show, and how would you make it add 3?

Answer

It shows 1. A setter only requests a change; count stays 0 for the whole handler, so all three requests set it to 1. Use the updater form setCount(c => c + 1), which React applies to the latest pending value, so three calls give 3.

Q20 · React：useEffect 与 socket

useEffect(() => {
  const s = new WebSocket(url);
  s.onmessage = (e) => setMessages(prev => [...prev, e.data]);
  return () => s.close();
}, []);

When does each part run? What changes if the dependency array is removed, or if the cleanup is removed?

Answer

The setup runs once after the first render and the cleanup runs when the component unmounts. Without the array, the effect runs after every render, so each render closes the old socket and opens a new one, which is wasteful. Without the cleanup, the socket stays open after unmount — a leak that keeps updating a dead component — and every remount adds another connection.

Q21 · React：key

A to-do list renders items.map((it, i) => <Row key={i} item={it} />), and each Row copies props.item into its own state. Deleting the first item makes the wrong row disappear. Why, and how would you fix it?

Answer

During reconciliation React matches old and new children by key. After deleting the first item the remaining items get keys 0..n−2, so React thinks the last row was removed and keeps the first Row instance, with its old state, at index 0. Use a stable unique id such as key={it.id} so each component instance stays attached to its own item.

Q22 · React：custom hook

Why refactor a to-do app’s list logic into useToDoItemList(), and how should the entry form and list display communicate with the app?

Answer

The custom hook separates business logic (the list state, add and delete) from display logic, so the component becomes a thin view and the logic can be reused and tested on its own; the hook’s state is still the component’s state, so its setters re-render the app. The app passes handleAdd to the form and items and handleDelete to the display as props, and the children call those handlers because props are read-only.

Q23 · Security：头像 URL

GameNite lets users save a profile-image URL that is shown to everyone in chat. Apply STRIDE to this data flow: name two threats and their mitigations.

Answer

Tampering: a malicious URL or script payload could be stored and rendered to other users, so validate it on the server with Zod (well-formed http/https only) and let React escape it. Spoofing / elevation of privilege: if the endpoint trusts a username in the request body, anyone could change someone else’s image, so take identity from the authenticated session. Denial of service from huge data URLs is mitigated by storing only a URL and limiting its length.

Q24 · Security：IP1 的密码泄露

IP1’s user service had 100% test coverage but still returned passwords. How is that possible, and why didn’t TypeScript stop it?

Answer

Coverage shows that lines and branches ran, not that the tests checked the right properties; no test asserted that the response lacked a password. TypeScript is structural, so an object with extra fields still matches the safe user type, and types are erased at runtime, so the extra field gets serialized. This is STRIDE information disclosure, fixed by explicitly building the safe object or stripping it with a schema.

Q25 · Security：前端防作弊

The Checkers client disables clicks for watchers and only highlights legal squares. Is the game safe from cheating?

Answer

No. Client code runs in an untrusted environment, and an attacker can send any request or websocket message directly. The server must validate the move’s shape with Zod, check that the sender is the current player, and check legality against its own game state; the client-side restrictions are only a convenience.

Q26 · Security：存密码

A teammate stores SHA-256(password) for each user. Is that enough?

Answer

No. Because people reuse passwords, attackers can hash password lists leaked from other sites and match them against your stolen hashes (rainbow tables). Use a random per-user salt and store hash(password + salt), using an established library rather than rolling your own.

Q27 · Security：admin 接口

An admin endpoint reads {userId, newRole} from the request body and checks whether that userId belongs to an admin. What is wrong, and which STRIDE category is it?

Answer

It is elevation of privilege (and spoofing): the requester chooses which identity gets checked, so any user can claim to be an admin. Authenticate through a server-side session or token, look up the logged-in user’s role, and authorize based on that; log role changes for non-repudiation.
